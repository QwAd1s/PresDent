# Структура платформы PresiDent

## 1. Роли и сценарии

| Роль | Что делает | Статус |
|---|---|---|
| **Администратор** | принимает заявки из WhatsApp/Instagram/сайта, отвечает в диалоге, записывает на приём, ведёт базу пациентов, отвечает на отзывы | реализовано (фронт + API) |
| **Владелец / управляющий** | смотрит аналитику, настраивает каналы и доступы, управляет врачами | частично (те же экраны) |
| **Врач** | видит своё расписание и пациентов | следующий этап |
| **Пациент** | оставляет заявку, смотрит врачей, расписание, отзывы, свою историю | следующий этап |

## 2. Разделы админ-панели

```
Главная            KPI: новые заявки, записи на сегодня, конверсия, время ответа;
                   график потока обращений (7 дней, по каналам), источники,
                   загрузка врачей, последние отзывы
Заявки             единый инбокс: фильтры по статусу и каналу, поиск;
                   карточка обращения = история диалога + ответ в тот же канал +
                   смена статуса/услуги + заметка
База пациентов     карточки, визиты, суммы, теги, лечащий врач, заметки
Врачи              рейтинг, загрузка, ближайшие окна, специализация
Расписание         недельная сетка по врачам, текущее время, карточка приёма
Отзывы             лента с оценками, распределение, публичный ответ
Каналы и интеграции статус WhatsApp/Instagram/сайта, URL вебхуков, журнал событий,
                   тестовая заявка, инструкция по подключению
Настройки          профиль клиники, SLA первого ответа, уведомления, команда и доступы
ИИ-админ           плавающий помощник на всех страницах: подсказка по разделам,
                   свободные окна, проверка занятости врача, запись пациента
```

Слева — постоянное меню с бейджами (новые заявки, отзывы без ответа) и индикаторами каналов.

## 3. Архитектура

```
WhatsApp Cloud API ─┐
Instagram Messaging ─┼─► POST /api/webhooks/*  ─► normalize ─► ingest() ─► store (JSON/PostgreSQL)
Форма на сайте ─────┤        (подпись HMAC)                      │
Телефония ──────────┘                                           ├─► SSE /api/events ─► React-админка
                                                                └─► channels.sendReply() ─► Graph API
```

Ключевая идея: **все каналы проходят через один нормализатор**. Дальше не важно, откуда пришло
сообщение — получается одна и та же заявка с полем `channel`. Поэтому новый канал (Telegram,
VK, Avito) добавляется одним парсером и не требует правок интерфейса.

### Поток входящего сообщения

1. Meta отправляет `POST` на `/api/webhooks/whatsapp` (или `/instagram`).
2. Сервер проверяет `X-Hub-Signature-256` по `META_APP_SECRET`.
3. Сразу отвечает `200` (Meta требует ответ за 20 секунд, иначе повторит событие).
4. Payload разбирается в `IncomingMessage { channel, externalUserId, name, text, at, externalId }`.
5. `ingestIncoming()`: если диалог с этим пациентом открыт менее 24 часов — сообщение
   добавляется в существующую заявку; иначе создаётся новая.
6. Заявка сохраняется, в SSE улетает событие `lead:new` / `lead:message` — админка обновляется
   без перезагрузки.
7. Ответ администратора: `POST /api/leads/:id/messages` → `sendReply()` → Graph API
   (`/{phone-number-id}/messages` или `/{ig-account}/messages`) → статус доставки в пузыре.

### Ограничение Meta, о котором нужно помнить

Отвечать свободным текстом можно только **в течение 24 часов** с последнего сообщения пациента.
Вне окна нужен утверждённый шаблон (message template). Для напоминаний о приёме — шаблоны
`appointment_reminder`, для отзыва — `review_request`.

## 4. Модель данных

```ts
Lead {            // заявка = диалог с пациентом по одному каналу
  id, channel: 'whatsapp' | 'instagram' | 'site' | 'phone',
  name, phone?, handle?, externalId?,      // externalId — wa_id / IGSID для ответа
  service?, status: 'new' | 'in_progress' | 'booked' | 'closed' | 'spam',
  priority: 'low' | 'normal' | 'high',
  unread, createdAt, updatedAt, assignee?, note?,
  messages: LeadMessage[]                   // direction: in | out + delivery
}

Patient { id, name, phone, birthDate?, since, visits, lastVisit,
          totalSpent, doctorId?, tags[], channel?, notes? }

Doctor { id, name, specialty, color, rating, reviewsCount, experienceYears,
         loadPercent, nextSlot, todayAppointments, workingDays[] }

Appointment { id, patientName, phone, doctorId, service, start,
              durationMin, status: 'confirmed' | 'waiting' | 'done' | 'cancelled', channel }

Review { id, author, rating, text, at, channel, answered, reply?, doctorId? }
```

Сейчас данные лежат в `server/data/db.json` (создаётся при первом запуске из `shared/fixtures.ts`).
Для продакшена — PostgreSQL + Prisma; схема выше переносится один-в-один.

## 5. API

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/stats` | KPI и графики для дашборда |
| GET | `/api/leads?status=&channel=&q=` | список заявок + счётчики статусов |
| PATCH | `/api/leads/:id` | статус, услуга, заметка |
| POST | `/api/leads/:id/messages` | ответ пациенту в его канал |
| POST | `/api/leads` | ручная заявка |
| GET | `/api/patients` · `/api/doctors` · `/api/appointments` | справочники |
| GET | `/api/reviews` · POST `/api/reviews/:id/reply` | отзывы и ответы |
| GET | `/api/channels` · POST `/api/channels/test` | статус каналов, тестовая заявка |
| GET | `/api/events-log` | журнал событий |
| GET | `/api/settings` · PUT `/api/settings` | настройки клиники |
| POST | `/api/assistant` | запрос к ИИ-админу: `{ text, page, pending? }` → ответ + слоты + действие записи |
| POST | `/api/appointments` | создать запись на приём с проверкой занятости (409 при конфликте) |
| GET | `/api/events` | SSE-поток для realtime |
| GET/POST | `/api/webhooks/whatsapp` · `/instagram` · `/site` | приём событий Meta и формы сайта |

## 6. Этапы развития

**Сделано**
- админ-панель: 8 разделов, дизайн-система, адаптив до планшета;
- единый инбокс заявок с историей диалога и отправкой ответов;
- приём вебхуков WhatsApp Cloud API и Instagram Messaging, проверка подписи, дедупликация по ID;
- журнал событий, тестовая заявка, SSE-обновление интерфейса;
- **ИИ-админ**: локальный движок (без внешних API) — интенты, свободные окна, проверка занятости, запись пациента с защитой от двойного бронирования;
- демо-режим фронтенда (интерфейс работает без API).

**Следующее**
1. **LLM для ассистента** — подключить модель через function calling к готовым инструментам (`freeSlots`, `createAppointment`, `getSchedule`), оставив ключ на сервере.
1. **Авторизация** — вход сотрудников (email + пароль / magic link), роли admin/owner/doctor, JWT-сессии.
2. **PostgreSQL + Prisma** — замена JSON-файла, миграции, индексы по `channel + externalId`.
3. **Очередь и ретраи** — BullMQ/Redis для исходящих сообщений и обработки вебхуков.
4. **Шаблоны WhatsApp** — напоминания о приёме, запрос отзыва, реактивация базы.
5. **Кабинет пациента** — запись онлайн, выбор врача и слота, история визитов, документы.
6. **Сайт клиники** — публичная часть: врачи, услуги, цены, отзывы; форма заявки уже умеет
   отправлять `POST /api/webhooks/site`.
7. **Уведомления** — Telegram-бот и e-mail администратору о новой заявке и о просроченном SLA.
8. **Аналитика** — воронка «обращение → запись → визит → повторный», отчёты по врачам и каналам.

## 7. Технические решения

- **SSE вместо WebSocket** — нужен только сервер→клиент поток, SSE проще и проходит через прокси (`proxy_buffering off`).
- **Единый ingestion-слой** — новый канал = один парсер, интерфейс не меняется.
- **Демо-фолбэк на фронте** — `src/lib/api.ts` при недоступном API переключается на `src/lib/mock.ts`, поэтому макеты можно показывать клинике без бэкенда.
- **Фикстуры в `shared/`** — одни и те же данные для сервера и демо-режима, нет расхождений.
- **Никаких секретов во фронтенде** — токены Meta живут только в `.env` на сервере.
