# PresiDent — платформа стоматологии

Админ-панель клиники, куда попадают заявки из **WhatsApp**, **Instagram**, с сайта и телефона.
Пациентские сценарии (личный кабинет, запись, отзывы) — следующие этапы, см. `STRUCTURE.md`.

**Стек:** React 19 + TypeScript + Vite · Node.js + Express · SSE для realtime · данные в JSON-файле (до подключения PostgreSQL).

## 1. Быстрый старт в VS Code

### 1.1 Проверьте Node.js

В терминале VS Code (`Ctrl + ~`):

```bash
node -v
npm -v
```

Если команда не найдена — установите **Node.js 22 LTS** с [nodejs.org](https://nodejs.org), затем **закройте и снова откройте VS Code** (чтобы подхватился PATH).

### 1.2 Установите зависимости

Терминал должен быть открыт в папке проекта (там, где лежит `package.json`):

```bash
cd C:\Users\fox\Documents\deepseek-harness\default-workspace\president
npm install
```

### 1.3 Запустите проект

```bash
npm run dev
```

Откройте в браузере: **http://localhost:5173**

Запустятся два процесса:

| Процесс | Адрес | Что делает |
|---|---|---|
| Vite (фронтенд) | http://localhost:5173 | админка с горячей перезагрузкой |
| API (Express) | http://localhost:8787/api | заявки, пациенты, вебхуки |

Файл `.env` не обязателен: без него сервер работает в демо-режиме (`DRY_RUN=true`) — сообщения не уходят в Meta, но вся логика приёма заявок работает.

### 1.4 Два способа запуска без терминала

- **Двойной клик по `start.cmd`** в папке проекта — сам проверит Node, при необходимости поставит зависимости, поднимет API и админку и покажет адрес.
- **F5 в VS Code** — в проекте есть `.vscode/launch.json` с конфигурацией *«PresiDent: API + админка»*. Выберите её в панели Run and Debug и нажмите ▶.

> Кнопка ▶ «Run» без выбранной конфигурации запускает `node` на текущем файле и падает с ошибкой `Cannot find module ...\run` — это не ошибка проекта, а неверный способ запуска.

### 1.5 Вход в систему

После запуска откроется страница входа. Демо-аккаунты (пароль у всех `president2026`):

| Роль | E-mail | Что видит |
|---|---|---|
| Владелец | `owner@president.ru` | всё, включая каналы и настройки |
| Администратор | `admin@president.ru` | заявки, пациенты, расписание, отзывы |
| Врач | `doctor@president.ru` | пациенты, врачи, расписание, отзывы — без заявок и настроек |

Пароль можно сменить в **Настройки → Безопасность**. Пароль сотрудников при первом создании базы задаётся переменной `SEED_PASSWORD`.

## 2. Что посмотреть в первую очередь

1. **Главная** — KPI, график потока обращений, последние заявки.
2. **Заявки** — таблица обращений, фильтры по каналам и статусам; клик по строке открывает карточку с историей диалога и полем ответа.

5. **Отзывы**, **База пациентов**, **Врачи**, **Настройки**.
6. **Сайт клиники** — публичная страница с онлайн-записью: пункт меню «Сайт клиники» или `http://localhost:5173/site` (раздел 12).

Отдельно стоит попробовать **сайт клиники с ИИ-помощником**: пункт «Сайт клиники» в меню или `http://localhost:5173/site` (разделы 12 и 8).

## 4. Подключение WhatsApp и Instagram

### 4.1 Что нужно от Meta

| Что | Где взять |
|---|---|
| App ID / App Secret | Meta for Developers → ваше приложение |
| WhatsApp Phone number ID | WhatsApp Manager → номер клиники |
| WhatsApp permanent token | System User с правом `whatsapp_business_messaging` |
| Instagram Page token | страница Facebook, связанная с IG-аккаунтом, права `instagram_basic`, `instagram_manage_messages`, `pages_messaging` |
| Instagram Account ID | ID профессионального аккаунта Instagram |

### 4.2 Публичный HTTPS-адрес для вебхуков

Meta не может постучаться на `localhost`. Для разработки поднимаем туннель:

```bash
npx ngrok http 8787
# или
cloudflared tunnel --url http://localhost:8787
```

Полученный `https://…` адрес записываем в `.env` → `PUBLIC_URL`.

### 4.3 Настройка `.env`

Скопируйте `.env.example` в `.env` и заполните:

```env
PORT=8787
PUBLIC_URL=https://your-tunnel.ngrok-free.app

WHATSAPP_VERIFY_TOKEN=president-wa-verify
WHATSAPP_TOKEN=EAAG...
WHATSAPP_PHONE_NUMBER_ID=1234567890

INSTAGRAM_VERIFY_TOKEN=president-ig-verify
INSTAGRAM_PAGE_TOKEN=EAAG...
INSTAGRAM_ACCOUNT_ID=17841400000000000

META_APP_SECRET=abc123...
DRY_RUN=false        # true — не отправлять сообщения, только логировать
```

### 4.4 Вебхук в Meta for Developers

- **Callback URL (WhatsApp):** `https://<туннель>/api/webhooks/whatsapp`
- **Verify token:** значение `WHATSAPP_VERIFY_TOKEN`
- Подписаться на поле `messages`.
- **Instagram:** Callback URL `https://<туннель>/api/webhooks/instagram`, поле `messages` (+ `messaging_postbacks`).

Meta сразу отправит `GET` с `hub.challenge` — сервер вернёт его, подписка подтвердится. Дальше каждое входящее сообщение превращается в заявку и приходит в админку без перезагрузки страницы (SSE).

### 4.5 Проверка руками

```bash
# 1) проверка подписки
curl "http://localhost:8787/api/webhooks/whatsapp?hub.mode=subscribe&hub.verify_token=president-wa-verify&hub.challenge=ok"

# 2) имитация входящего сообщения от Meta
curl -X POST http://localhost:8787/api/webhooks/whatsapp \
  -H "Content-Type: application/json" \
  -d "{\"object\":\"whatsapp_business_account\",\"entry\":[{\"changes\":[{\"value\":{\"contacts\":[{\"profile\":{\"name\":\"Иван\"},\"wa_id\":\"79001234567\"}],\"messages\":[{\"from\":\"79001234567\",\"id\":\"wamid.X\",\"timestamp\":\"1764000000\",\"type\":\"text\",\"text\":{\"body\":\"Сколько стоит имплантация?\"}}]}}]}]}"
```

Ответ `200`, а заявка появляется в админке (в демо-режиме — сразу, в live — после подписки на вебхук).

## 5. Деплой

### Вариант A. Docker Compose — быстрее всего

В репозитории есть `Dockerfile` и `docker-compose.yml`: приложение + PostgreSQL 16, том для данных, health-check и авто-рестарт.

```bash
cp .env.example .env      # при желании поменяйте пароли
docker compose up -d --build
# открыть http://localhost:8787
```

Что происходит: Postgres поднимается и ждёт `pg_isready`, приложение стартует после него с `DB_DRIVER=postgres`, при первом запуске база засеивается демо-данными (потом данные живут в томе `pgdata`).

Полезные команды:

```bash
docker compose logs -f app     # логи приложения
docker compose exec db psql -U president -d president   # консоль БД
docker compose down            # остановить (данные сохранятся в томе)
docker compose down -v         # остановить и удалить данные
```

Для домена с HTTPS: тот же compose, но `COOKIE_SECURE=true`, `PUBLIC_URL=https://crm.clinic.ru` и nginx с сертификатом перед контейнером (см. вариант B).

### Вариант B. Один VPS без Docker (проще всего, всё на одном домене)

```bash
# на сервере (Ubuntu)
git clone <repo> /var/www/president && cd /var/www/president
npm install
npm run build
cp .env.example .env   # заполнить токены, PUBLIC_URL=https://crm.clinic.ru
```

Процесс-менеджер:

```bash
npm i -g pm2
pm2 start "npm start" --name president
pm2 save && pm2 startup
```

Nginx как reverse proxy с HTTPS (обязательно — Meta требует валидный сертификат):

```nginx
server {
    listen 443 ssl;
    server_name crm.clinic.ru;

    ssl_certificate     /etc/letsencrypt/live/crm.clinic.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/crm.clinic.ru/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8787;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_buffering off;   # важно для SSE (/api/events)
    }
}
```

`certbot --nginx -d crm.clinic.ru` — сертификат.

### Вариант C. Render / Railway

- Один Web Service из репозитория: `Build: npm install && npm run build`, `Start: npm start`.
- Переменные окружения — из `.env.example`.
- **База:** создайте PostgreSQL в панели Render и передайте `DATABASE_URL` в сервис, добавив `DB_DRIVER=postgres`. Без этого данные живут в эфемерном JSON-файле и пропадут при рестарте.
- Публичный адрес сервиса сразу годится как `PUBLIC_URL` для вебхуков.

### Вариант D. Vercel (фронтенд) + отдельный API

- фронтенд: Vercel, переменная `VITE_API_URL=https://api.clinic.ru`;
- API: Render/Railway/VPS; CORS уже разрешён в `server/index.ts`.

> Для реальных пациентов обязательны: авторизация сотрудников, PostgreSQL вместо JSON-файла, резервные копии и 152-ФЗ (хранение медданных в РФ).

### Чек-лист перед публикацией

| Что | Значение | Зачем |
|---|---|---|
| `NODE_ENV` | `production` | включает флаг `Secure` у cookie сессии |
| `SEED_PASSWORD` | свой пароль | иначе останется демо-пароль `president2026` |
| `DB_DRIVER` + `DATABASE_URL` | `postgres` + строка подключения | данные переживут рестарт и деплой |
| `PUBLIC_URL` | `https://ваш-домен` | адрес вебхуков для Meta |
| `DRY_RUN` | `false` | сообщения реально уходят пациентам |
| `META_APP_SECRET` | секрет приложения | проверка подписи вебхуков |
| `COOKIE_SECURE` | `true` (если HTTPS терминируется прокси) | cookie только по HTTPS |
| Бэкапы | `pg_dump` по cron + хранение 30 дней | восстановление после сбоя |
| Мониторинг | `GET /api/health` каждую минуту | видно драйвер БД, режим отправки, число сущностей |

**Проверка после деплоя:** открыть `/login` → войти → `/site` → оформить тестовую запись → увидеть заявку в админке → `/api/health` показывает `driver: postgres`.

## 7. Частые проблемы

| Симптом | Причина и решение |
|---|---|
| `npm: команда не найдена` | не установлен Node.js или VS Code не перезапущен после установки |
| `Cannot find module ...\president\run` | запустили `node run` или нажали ▶ без конфигурации — используйте `npm run dev`, `start.cmd` или F5 с конфигурацией из `.vscode/launch.json` |
| Порт 5173 занят | Vite выберет 5174 — смотрите вывод в терминале |
| Порт 8787 занят | `PORT=8788 npm run dev:api` (и прокси в `vite.config.ts`) |
| Бейдж «Демо-режим» | API не запущен: `npm run dev:api`; данные тогда живут только в браузере |
| Meta пишет «Callback verification failed» | `PUBLIC_URL` недоступен извне или verify-token не совпал с `.env` |
| Вебхук отвечает 401 | заполнен `META_APP_SECRET`, но подпись не совпала — проверьте, что тело запроса не меняется прокси |

## 8. ИИ-помощник пациента

Живёт на **сайте клиники** (`/site`): кнопка «Помощник клиники» в правом нижнем углу. В админке его нет — администратору он не нужен, а пациенту помогает выбрать услугу и время.

### Что умеет

| Вопрос | Ответ |
|---|---|
| «сколько стоит имплантация», «а чистка?» | цена, длительность и что входит в услугу |
| «есть ли окно завтра у гигиениста» | свободные окна врача на дату, кнопки времени |
| «можно записаться в субботу на чистку» | подбирает врача по услуге и показывает окна |
| «болит зуб, что делать» | телефон клиники + ближайшие окна на сегодня (или завтра) |
| «какие у вас врачи» | список специалистов по направлениям |
| «как подготовиться к приёму» | что взять, можно ли есть, как быть, если страшно |
| «где вы и до скольки работаете» | адрес, часы, телефон, почта |

Клик по времени подставляет **услугу, врача, дату и слот** в форму записи и прокручивает к ней — пациенту остаётся ввести имя и телефон.

### Как устроено

- Движок — `shared/patient-assistant.ts`: чистые функции, разбор фраз (услуга, врач, «завтра/в субботу», время), расчёт окон через `shared/slots.ts`.
- Сервер отдаёт **только открытые данные**: услуги, врачи, свободное время, контакты. Ни заявок, ни телефонов пациентов, ни истории — в отличие от старого админского ассистента.
- `POST /api/public/assistant` без авторизации, но с лимитом 80 вопросов в час с одного IP.
- Запись по-прежнему идёт через `POST /api/public/book` с серверной проверкой занятости.

### Когда появится LLM

Интерфейс готов к замене «понимания» на модель:

1. `AI_PROVIDER` и `AI_API_KEY` в `.env` (ключ только на сервере).
2. В `server/public-routes.ts` вызов `patientAssistantReply(...)` меняется на запрос к модели с инструментами: `freeSlots`, `servicesCatalog`, `doctorsList`.
3. Промпт-заготовка: «Ты администратор стоматологии PresiDent. Отвечай коротко, называй только цены из каталога, перед записью проверяй свободные окна».

## 9. Авторизация и роли

### Как устроено

- **Пароли** — scrypt с солью (`server/password.ts`), хеш вида `scrypt$N$r$p$salt$hash`. В открытом виде пароли не хранятся и наружу не отдаются.
- **Сессии** — серверные, случайный 32-байтный идентификатор в httpOnly-cookie `president_session` (`SameSite=Lax`, `Secure` при `NODE_ENV=production`). Живут 7 дней, хранятся в базе, поэтому выход и смена пароля их реально отзывают.
- **Защита API** — middleware `authGate` (`server/auth.ts`) пускает без входа только: `/api/health`, `/api/auth/login` и вебхуки WhatsApp/Instagram/сайта. Всё остальное требует сессии.
- **Роли** — `allow('owner','admin')` на заявках, каналах, настройках и отзывах. Врач получает `403` — это проверено тестами.
- **Подбор пароля** — после 6 неудачных попыток за 10 минут аккаунт+IP получают `429`.
- **Смена пароля** завершает все остальные сессии сотрудника.

### Матрица доступа

| Раздел / действие | owner | admin | doctor |
|---|---|---|---|
| Главная (KPI) | ✅ | ✅ | redirect на расписание |
| Заявки, ответы, статусы | ✅ | ✅ | ❌ |
| Пациенты, врачи | ✅ | ✅ | ✅ |
| Расписание, создание записи | ✅ | ✅ | ✅ |
| Отзывы, публичный ответ | ✅ | ✅ | чтение |
| Каналы, журнал событий, тестовая заявка | ✅ | ✅ | ❌ |
| Настройки клиники, команда | ✅ | ✅ | ❌ |
| Смена своего пароля | ✅ | ✅ | ✅ |

### Что стоит знать

- Пароль в демо-базе задаётся `SEED_PASSWORD` при **первом** создании `server/data/db.json`. Если база уже есть, смена переменной её не перезапишет — удалите файл или смените пароль в интерфейсе.
- `db.json` теперь версии 3: при старте старый файл пересоздаётся, поэтому демо-данные и записи сбросятся один раз.
- CSRF закрыт связкой `SameSite=Lax` + JSON-тела запросов; при выносе API на отдельный домен понадобится `SameSite=None; Secure` и allowlist Origin.
- Демо-режим (без API) сохраняет вход в `localStorage` — это только для показа интерфейса, не для реальных данных.
- Следующий шаг по безопасности: приглашения сотрудников, гибкие права, TOTP-двухфакторка и журнал действий с привязкой к пользователю.

## 10. Записи на приём и услуги

### Справочник услуг

`shared/services.ts` — единый источник цен, длительности и специализации: 11 услуг с категориями (`Диагностика`, `Гигиена`, `Терапия`, `Хирургия`, `Ортопедия`, `Ортодонтия`, `Эстетика`, `Детям`). На него опираются:

- форма записи и карточка заявки (цена и длительность видны сразу);
- ИИ-помощник пациента (подбор врача по услуге и расчёт окон);
- расчёт свободных слотов.

Цены — демонстрационные, меняются в одном файле. Следующий шаг — редактирование каталога из «Настроек».

### Как работает запись

1. Форма берёт врача, услугу и дату — сервер возвращает реальные свободные окна: `GET /api/slots?doctorId=doc-4&date=2026-11-27&service=Гигиена и чистка`.
2. Слоты считаются по рабочему окну клиники (будни 9–21, вс 10–18), рабочим дням врача, длительности услуги и уже существующим приёмам. Отменённые приёмы окно не занимают.
3. Создание: `POST /api/appointments` — при пересечении вернёт `409`, форма предложит другое время.
4. **Перенос:** `POST /api/appointments/:id/reschedule` — та же проверка занятости, в заметку пишется, откуда перенесли.
5. **Статусы:** `confirmed` → «Пациент пришёл» (`waiting`) → «Завершён» (`done`); отмена — `cancelled` с причиной. Все изменения видны на дашборде и приходят в интерфейс по SSE.
6. Из карточки заявки кнопка «Записать на приём» открывает расписание с уже подставленными именем, телефоном и услугой; после создания заявка автоматически переходит в статус «Записан».

### Идемпотентность и повторные попытки

Проверка конфликтов идёт на сервере, поэтому даже при одновременной записи двух администраторов второй получит `409`, а не двойную запись. Это же правило использует ИИ-помощник.

## 11. Сотрудники и журнал действий

### Управление командой (только владелец)

**Настройки → Команда и доступы**:

- **«Пригласить»** — имя, e-mail, роль; для врача нужно выбрать карточку из справочника. Пароль можно задать сразу или оставить пустым — сервер сгенерирует временный и покажет **один раз** (его нужно передать сотруднику).
- **Смена роли** прямо в строке: `owner` / `admin` / `doctor`. При снятии роли врача привязка к врачу очищается.
- **«Отключить»** — доступ блокируется, все сессии сотрудника завершаются немедленно; вход вернёт `403 «Доступ отключён»`. Включить обратно можно той же кнопкой.
- **«Сбросить пароль»** — генерирует новый временный пароль и отзывает сессии; старый пароль перестаёт работать.
- Защита от ошибок: нельзя сменить собственную роль, отключить себя или оставить клинику без владельца.

### Журнал действий

Раздел **«Журнал действий»** (`/audit`, виден владельцу и администратору) — лента изменений с фильтрами по типу, поиском и **экспортом в CSV**.

Пишутся события: вход и выход, смена пароля, завершение сессий, создание и смена статуса заявки, ответы пациентам, создание/перенос/отмена приёма, ответы на отзывы, изменение настроек, любые действия с сотрудниками. Каждая запись — кто, когда, что и над каким объектом.

Журнал хранит последние 800 событий в базе и обновляется по SSE без перезагрузки страницы. Для полноценного аудита (срок хранения, IP, выгрузка за период) понадобится таблица в PostgreSQL.

## 12. Сайт клиники и онлайн-запись

Публичная часть — **http://localhost:5173/site** (в админке есть пункт «Сайт клиники» в меню). Авторизация не нужна.

### Что на странице

- герой с преимуществами и живой карточкой «Ближайшие окна» (врачи и рейтинг из базы);
- **услуги и цены** из справочника, клик по услуге сразу переносит к форме записи с выбранной услугой;
- **врачи**: специализация, стаж, рейтинг, дни приёма;
- **онлайн-запись**: услуга → врач (подставляется по специализации) → дата → **реальные свободные окна** → имя и телефон → подтверждение с адресом и ценой;
- подвал с адресом, телефоном и входом для сотрудников.

В правом нижнем углу — **ИИ-помощник** (раздел 8): отвечает на вопросы о ценах, врачах и свободном времени и подставляет выбранный слот в форму записи.

### Что происходит после записи

1. Проверяется занятость слота; если его только что заняли — `409` и форма сразу обновляет окна.
2. Создаётся **приём** (`status: confirmed`, канал `site`) — он сразу виден в расписании админки.
3. Создаётся **пациент**, если такого телефона ещё нет в базе (тег «Онлайн-запись»).
4. Создаётся **заявка** со статусом «Записан» и сообщением о записи — администратор видит её в инбоксе.
5. В **журнал действий** пишется `appointment.create` от имени «Сайт клиники».

### Защита

- валидация имени, телефона (10+ цифр), услуги, врача и времени;
- проверка пересечений на сервере — двойная запись невозможна;
- лимит **8 заявок с одного IP в час**, дальше `429` с предложением позвонить;
- публичный API не отдаёт ничего лишнего: ни телефонов пациентов, ни истории, ни заявок.

### Публичный API

```
GET  /api/public/clinic                       клиника, услуги, врачи, цифры доверия
GET  /api/public/slots?doctorId=&date=&service=  свободные окна (только время)
POST /api/public/book                         запись: name, phone, service, doctorId, start, comment?
```

Открыт без сессии, но изолирован от служебных ручек: `/api/leads`, `/api/patients` и остальное по-прежнему требуют вход.

## 13. База данных

Хранилище переключается переменной `DB_DRIVER` — код приложения не меняется.

| Драйвер | Когда использовать | Настройка |
|---|---|---|
| `json` | по умолчанию, «поставил и забыл» | файл `server/data/db.json` |
| `pglite` | локальная разработка с настоящим Postgres, без установки сервера | `DB_DRIVER=pglite`, папка `PGLITE_DIR` |
| `postgres` | продакшн (Render, VPS, Railway) | `DATABASE_URL=postgresql://…` |

```env
# локально, полноценный Postgres в WASM
DB_DRIVER=pglite
PGLITE_DIR=server/data/pglite

# продакшн
DB_DRIVER=postgres
DATABASE_URL=postgresql://user:pass@host:5432/president?sslmode=require
```

### Как устроено

- Таблица `entities (type, id, ord, data jsonb, updated_at)` — «документный» слой: одна строка на заявку, приём, пациента, сотрудника, сессию, запись аудита. Отдельная таблица `meta` хранит версию сида.
- Чтение — из памяти процесса (быстро, без JOIN-ов); запись — **диффом в транзакции**: сохраняются только изменённые сущности, каждые ~120 мс после последнего изменения.
- При остановке (`Ctrl+C`, SIGTERM) сервер досохраняет всё и закрывает соединение — данные не теряются.
- Сид применяется **только к пустой базе**. Если база уже с данными, версия фикстур ничего не перетирает (в логе будет предупреждение).
- `GET /api/health` показывает текущий драйвер и количество сущностей.

### Проверено

```
старт с DB_DRIVER=pglite       → «пустая база: загружены демо-данные», 12 заявок
онлайн-запись + новый сотрудник + смена статуса приёма
остановка сервера
повторный старт                → заявок 13, пациентов 11, приёмов 11, сотрудников 4
                               → заявка, приём (status waiting), пациент, аудит и сотрудник на месте
DB_DRIVER=json                 → тот же сценарий, данные в server/data/db.json
```

### Ограничения и следующий шаг

Документный слой рассчитан на одну клинику и один процесс записи — этого достаточно для стоматологии (десятки тысяч строк). Когда понадобятся отчёты по большим периодам, нормализуем таблицы (`leads`, `appointments`, `messages`, `patients`) и перейдём на репозитории: маршруты уже ходят через `getDb()`, поэтому изменения будут локальными в слое хранилища.

## 14. Напоминания пациентам

Раздел **«Напоминания»** в меню (владелец и администратор) — очередь сообщений и журнал отправок.

### Что и когда отправляется

| Событие | Когда | Текст |
|---|---|---|
| Напоминание о приёме | за `reminderHours` часов до визита (по умолчанию 24) | «Здравствуйте, Мадина! Напоминаем: 28 ноября, 10:30 у вас приём — Гигиена и чистка, врач Байсултанов Ислам Вахаевич. Адрес: … Если планы изменились, ответьте — перенесём.» |
| Запрос отзыва | через `reviewDelayHours` часов после приёма (по умолчанию 2) | «Мадина, спасибо, что были в PresiDent! Оцените приём по шкале от 1 до 5…» |

Интервалы меняются в **Настройках → Уведомления и SLA**.

### Как работает

- Планировщик стартует вместе с сервером и раз в минуту создаёт недостающие задачи и отправляет просроченные (`REMINDERS_TICK_MS`).
- Создание **идемпотентно**: повторный прогон не плодит дубли на один и тот же приём.
- Отмена приёма автоматически снимает его напоминания с очереди (статус «Пропущено»).
- Кнопка **«Разослать сейчас»** запускает планирование и отправку вручную, кнопка «Пропустить» убирает конкретное сообщение.
- Ошибки отправки повторяются до 3 раз с интервалом 10 минут, после — статус «Ошибка» с текстом причины.

### Каналы и режимы

Канал выбирается автоматически: `whatsapp`, если он подключён и не `DRY_RUN`; иначе Telegram (если настроен бот), иначе SMS-провайдер. Пока провайдер не настроен, сообщение получает статус **«Демо-отправка»** — текст готов, пациенту ничего не уходит. Это видно в интерфейсе и статистике, поэтому «тихую» потерю сообщений не пропустить.

```env
REMINDERS_ENABLED=true
REMINDERS_TICK_MS=60000
TELEGRAM_BOT_TOKEN=...        # бот для напоминаний и уведомлений сотрудникам
TELEGRAM_STAFF_CHAT_ID=...    # чат клиники: новые заявки
SMS_API_URL=...               # любой HTTP-провайдер с Bearer-токеном
SMS_API_KEY=...
```

### API

```
GET  /api/reminders?status=pending   очередь и статистика
POST /api/reminders/run              спланировать и отправить просроченные
POST /api/reminders/:id/skip         убрать из очереди
```

### Проверено

```
старт сервера               → планировщик создал 10 задач, 9 сразу ушли в «Демо-отправку»
повторный прогон            → created 0 (идемпотентность)
новая запись на +2 дня      → создано 1 напоминание, sendAt = приём − 24 ч
ручной пропуск              → статус skipped
отмена приёма               → его напоминание стало skipped
перезапуск сервера (pglite) → 13 задач на месте, пропущенные и оба типа сохранились
```
